# Benchmark report: `rupi` vs `pi`

Status: Complete — all ten cases measured for both agents.

This report records a fresh-memory comparison of `rupi` and Pi 0.86.1 on the ten
repository evaluation cases under [`cases/`](../../cases/). The fixed inference
server is llama.cpp serving Qwen 3.8 Flash Next (UD-IQ4_XS).

Execution window: 2026-09-20 23:23 through 2026-09-21 02:21
America/New_York. The two raw runs are `bench-20260920-01-05` and
`bench-20260921-06-10`. Their machine-readable results, traces, session logs,
verification output, and scratch workspaces are under the ignored
`.benchmark/runs/` directory. No implementation or acceptance case files were
changed by the benchmark.

The quantitative result tables and raw run evidence are generated under the ignored
`.benchmark/` directory. The checked-in harness is
[`bench/compare-pi-rupi.ps1`](../../bench/compare-pi-rupi.ps1).

## Executive summary

Neither agent reached an acceptance-oracle resolution on any case within the
two-turn budget: 0/10 cases for `rupi`, 0/10 for Pi. All 20 agent/case runs also
returned nonzero project-test and acceptance-oracle results after their final
attempt. Therefore, there is no successful turns-to-resolution winner in this
sample; every result is censored at `>2` turns.

| Agent | Oracle resolutions | Input tokens | Output tokens | Total tokens | Agent wall time | Median case wall | Timed-out turns |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `rupi` | 0/10 | 308,358 | 15,404 | 323,762 | 4,026.9 s | 365.0 s | 6/20 |
| `pi` | 0/10 | 49,685 | 22,233 | 71,918 | 6,004.4 s | 600.4 s | 20/20 |

The headline tradeoff is not “Rupi is faster”: Rupi used 4.50 times as many
measured tokens overall and often terminated early with a nonzero process exit,
while Pi used fewer tokens but reached the five-minute cap on every turn. Rupi's
lower aggregate wall time is therefore dominated by early failed exits, not by
verified task completion. Pi produced more visible implementation output in
several cases, especially Event Outbox, Webhook Inbox, and Receipt Ledger, but
that output did not close the test/oracle loop.

My tester judgment from this single sample is that neither runtime is reliable
for unassisted completion of this ten-case ladder with this quantized local model
and two-turn budget. The dominant failure mode was failure to reach a verified
end state, not merely a cosmetic difference in final prose. Pi showed stronger
visible batch-writing behavior in some cases; Rupi showed heavier context and
inspection/`exec` activity and partial progress in other cases. Those are useful
behavioral clues, not general claims about the agents outside this protocol.

## Research questions

1. How many agent turns are required before the independent acceptance oracle passes?
2. How many provider input/output tokens are consumed?
3. How much wall-clock time elapses in agent execution and through independent
   resolution verification?
4. How do the agents differ in tool use, recovery behavior, intermediate quality,
   and final artifacts?

  are relevant latency limitations for this result.
- Each case starts from a clean scratch workspace containing only its specification,
  configuration files, and ignore rules. Existing implementations and prior case
  reports are not copied into the agent workspace.
- Each agent receives the same neutral implementation prompt and at most one
  standardized recovery prompt. A turn is one CLI invocation/user request; internal
  provider requests are counted separately.
- The neutral prompt required reading `SPEC.md`, building the complete
  dependency-free Python 3 project, adding a readable README and focused unittest
  tests, using standard-library modules, working only inside the project
  workspace, and reporting exact command statuses. The recovery prompt asked the
  agent to inspect the current workspace and finish the incomplete implementation.
- The acceptance oracle was copied into a separate sibling directory and was not
  exposed to either agent. It was run in a fresh process after every attempted
  turn, together with the project test command and case-specific help commands.
- The client-side benchmark policy is also fixed: thinking level `low`, a maximum
  of 8 model requests per Rupi turn, and a maximum output budget of 16,384 tokens
  for both clients. These settings are normalization choices for the comparison;
  the llama.cpp server command remains the requested one. Rupi's CLI invocation
  used `--no-reasoning` for its user-facing surface; Pi used `--thinking low`.
- A case is resolved only when the unchanged, fresh-process acceptance oracle exits
  zero. Agent prose and self-reported test results are not acceptance evidence.
- Raw stdout, stderr, traces/session logs, generated files, verification output, and
  machine-readable summaries remain in `.benchmark/` and are ignored by Git.

Turns-to-resolution is the first attempted turn whose post-turn oracle exits zero;
an unresolved case is shown as `>2`. Input/output/total tokens are the usage fields
exposed by the clients or runtime and do not claim to recover hidden reasoning
tokens. Agent wall time is the sum of CLI invocation elapsed times and excludes
independent verification. Qualitative observations use visible tool names,
verification output, and final filesystem snapshots only.

### Qualitative comparison

Pi made more visible source-file progress on Event Outbox, Webhook Inbox, and
Receipt Ledger, while Rupi produced partial package files on Artifact Pipeline and
Lease Fence where Pi left only the baseline. This is an outcome observation, not an
acceptance claim: all 20 final project-test and independent-oracle checks returned
nonzero. Rupi's traces show repeated `read`/`exec` activity and much larger input
totals; Pi's traces show shorter context totals but more `write`/`edit` activity
when it began implementation batches. Tool names are descriptive only; the raw
traces and generated-file snapshots are the evidence.

Rupi recorded 70 model requests and 61 tool requests. Its visible tool mix was

oracle boundary within the two-turn budget.

## Limitations and interpretation

The results are censored by the two-turn and 300-second-per-turn limits: `>2` is
not evidence that an implementation would never converge. The model uses
temperature `1.0`, so this is one stochastic sample per agent/case, not an
estimate of a distribution. Pi 0.86.1 and the current Rupi binary are compared
as user-facing runtimes, so wrapper and tool-surface differences are part of the
observed behavior. The clients share the model endpoint and key generation
parameters, but their prompt/session formats and tool adapters are not identical.
Pi used its `bash` tool while Rupi used its available `exec`/PowerShell-oriented
surface, which is a Windows environment confound. Verification commands ran
independently after every turn; acceptance is based only on the unchanged oracle
exit code. No tester repair or manual patching was allowed.

The IQ4_XS sample and the long, dependency-free multi-file contracts exposed
tool-calling and completion weaknesses in both wrappers. That is an inference from
the traces and outcomes, not a causal diagnosis: this benchmark did not run
controlled ablations of prompt, model quantization, timeout, or client policy.

## Conclusion

Under this fixed Qwen 3.8 Flash Next IQ4_XS setup, neither `rupi` nor Pi resolved
any of the ten internal cases within two turns. Pi was much more token-efficient
and visibly wrote broader partial implementations in several cases, but every
turn timed out. Rupi consumed substantially more context and total tokens and
frequently exited nonzero before the cap, while still producing partial work on
some deeper cases. A useful follow-up is a controlled repeat with more turns and
a larger per-case wall budget, followed by repeated samples per case; this report
should not be read as a general ranking beyond the stated protocol.
